**为什么 08 延后（实测为据，不是偷懒）**：`nodes` 现有 8 个索引，`whereOf` 的身份过滤是三列
`(col='' OR col=?)`——SQLite 无论加不加 `created_at` 索引都必须 `USE TEMP B-TREE FOR ORDER BY`；
5000 行实测 `offset 3000` 0.516 ms vs 游标深页 0.474 ms（≈无差）；当前 live 仅 817 节点。
所以 keyset 的真实收益是「写入并发下不跳页/不重页」，不是性能；而代价是 API 契约变更 + 客户端翻页重写 +
4 个既有测试文件改写。**当前规模不值得**，记入延后（触发：库 >5 万节点或面板翻页 >200ms）。

## 3. 契约（r2 钉死）

### 3.1 鲸忆 03：判重候选并集（免费半）

- **最近窗口保持不变**：`CANDIDATE_LIMIT = 300`（`decide.js:9`，不是 12；12 是 `queue.js:23`
  的 `JUDGE_CANDIDATE_LIMIT`，只用于 judge prompt）。
- 并集：`findCandidatesWithFts(db, event)` = 最近 300（顺序不变）∪ `ftsCandidateRows({query:event.text, identity, limit:12})`，
  按 id 去重、最近在前；上限 **312**（截断时 `ftsStats.truncated += 1`，可读）。
- **FTS 候选必须与最近候选同字段集**：共用 `CANDIDATE_FIELDS`（`id,text,level,memory_type,source,valid_at,invalid_at`）——
  现有 `collectFts` 不取 `valid_at/invalid_at`，直接并进判重循环会把「已失效旧事实」当恒重叠 →
  误 `SUPERSEDE/REVIEW`。这是 r2 新增的硬约束。
- **相似度闸（r2 新增，防误降级）**：候选并集里取 `similarity(event.text, row.text)` 最高的一条；
  仅当 **`sim ≥ 0.35` 且 共享检索词 ≥2**（用 `buildPlan(event.text)` 的词项与候选正文求交）时，
  才在「字面六分支全未命中」后改出 `CANDIDATE`（reason `paraphrase_suspect`）。
  否则维持原 `ADD reason='new'`。反例（必须仍 ADD）：「全量门禁这套流程太慢了」（sim≈0.09）。
- **本能力不解决"零字面交集的真同义句"**：实测「发版之前要先把整套校验都过一遍…」对
  「发布前必须跑全量门禁并检查退出码…」FTS 命中 **0**，仍会 ADD。文档与 CHANGELOG 必须写明这条限制
  （真同义判重仍属延后 §1.2，需模型/embedding）。
- 其余判据顺序（hash/字符袋/矛盾/包含/近文/语序）**逐条不变**；不自动 MERGE、不改正文、不丢数据。
- 表征测试先行：先锁六分支结论 + 「弱相关必须 ADD」+ 「judge=llm 候选集不变」，再实现并集。

### 3.2 人设 P1：远端读面收口（两语：zh/en）

- `panel.allowRemote=false`：现行为不变（非回环一律 403）。
- `panel.allowRemote=true` 且**非回环**：`GET /config`、`GET /persona` → 403 `read_only_remote`；
  `GET /personas` → 200 但**脱敏**：去掉 `bots.*.private.bindings`（目标号）、去掉绝对路径（只留 key/名/来源/是否绑定布尔）；
  `GET /resolve` 保留（面板调试用，不含正文）。
- 新增错误码 `read_only_remote` 已在码表（复用）；人设仓无 `err.*` 码表 → 只加 `locale/zh,en` 两条文案或用 `[code]` 透出，
  **不新建码表**（r2 明确：两语，不碰三语体系）。
- 判据：非回环 harness 用例（伪造 peer）→ `/config` 403、`/persona` 403、`/personas` 200 且响应体不含 `bindings` 目标号与绝对路径；
  回环下三者照常 200。

### 3.3 人设 P2：保存回读语义

- 现状：`POST /config` 返 `{ok, memoryHinted, memoryHint, mirrorSynced}`；`commitConfig` 已写盘。
- 契约：写盘成功后**回读 `config.json` 并校验 `dsh/bots` 关键字段**；回读失败/不一致 → 仍 `ok:true`，
  另带 `readBackFailed:true` + `readBackReason`（短码，无正文）；只有**写盘失败**才 `ok:false`（501）。
- 面板：`readBackFailed` → 文案「已保存·回读失败，重启后以文件为准」，不得再说「保存失败」；
  真失败仍显示失败（保留反向用例）。
- 判据：桩 commitConfig 成功 + 回读抛错 → `ok:true,readBackFailed:true` 且配置已落盘；写盘失败 → 501。

## 4. 构建与基线策略（r2：形状基线随 commit 刷新）

- 生成物：鲸 `i18n-check --write` / `manual-build --write` / `build-client`；人设同构（两语）。
- **门禁顺序固定**：改代码 → 定向用例 → `capture-baseline`（形状/产物基线）+ `lint-size --write` →
